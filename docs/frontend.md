# Веб-интерфейс Life Hub

React + TypeScript + Vite, адаптивный интерфейс для авторизации и планирования. Рабочие разделы: «Мой день», календарь дня/недели, списки и настройки. В «Моём дне» доступны фильтры «На день», «Предстоящие», «Все задачи» и «Готово». Цели, здоровье, финансы, книги и дневник обозначены серыми пунктами «coming soon».

Вход, регистрация, подтверждение почты шестизначным кодом, повторная отправка и восстановление пароля используют Python API. После первого входа пользователь задаёт имя и часовой пояс. Новый аккаунт выбирает только планирование; прежний выбор модулей существующего аккаунта сохраняется. Free выбран по умолчанию. Пробные 72 часа запускаются только после явного выбора пользователя; платёжного интерфейса нет.

## Запуск

Полное приложение из корня проекта:

```powershell
docker compose up --build -d
```

Открыть [Life Hub](http://127.0.0.1:5173). Сервис `frontend` отдаёт собранный интерфейс через Nginx и проксирует `/api/` к сервису `api:8000`. API также доступен напрямую: [Swagger](http://127.0.0.1:8000/docs). Начальная подготовка Python, `.env` и БД описана в [README](../README.md).

Для разработки нужны Node.js 24, pnpm 11.19.0 и работающий backend:

```powershell
cd frontend
pnpm install --frozen-lockfile
pnpm dev
```

Vite использует [http://127.0.0.1:5173](http://127.0.0.1:5173) и проксирует `/api` на `http://127.0.0.1:8000`. Если Docker-фронтенд уже занял порт, остановите его из корня проекта командой `docker compose stop frontend`. Бэкенд, worker и БД продолжают работать.

Обычный запуск использует один origin для страницы и запросов: CORS дополнительно не требуется. При внешнем размещении нужны HTTPS и корректная конфигурация прокси. Для Vite можно задать другой адрес API через серверную переменную `LIFEHUB_API_TARGET` до запуска `pnpm dev`.

## Реальный аккаунт и демо

Реальные access/refresh-токены сохраняются в `sessionStorage` текущей вкладки; постоянное хранение реальных токенов в `localStorage` не используется. Обновление access выполняется автоматически, параллельные запросы используют одну операцию refresh. Выход очищает локальную сессию и запрашивает отзыв refresh на сервере. Если браузер запретил storage, текущая сессия работает в памяти.

«Сначала осмотреться» включает явно обозначенное демо с примерами. Демо хранит отдельные данные в `localStorage`, поэтому примеры и изменения сохраняются между посещениями. Оно не создаёт серверный аккаунт, не отправляет письма и не подключает реальные календари или модель ИИ. Для реальных данных нужен обычный вход.

## Публичная конфигурация фронтенда

При разработке создайте `frontend/.env.local` по образцу `frontend/.env.example`. Здесь допустимы только публичные идентификаторы:

```dotenv
VITE_GOOGLE_CLIENT_ID=
VITE_APPLE_CLIENT_ID=
VITE_APPLE_REDIRECT_URI=
```

| Переменная | Что указать |
|---|---|
| `VITE_GOOGLE_CLIENT_ID` | OAuth Client ID типа Web application из Google Auth Platform, обычно заканчивается на `.apps.googleusercontent.com`. Этот же ID должен входить в серверный `LIFEHUB_GOOGLE_CLIENT_IDS`. |
| `VITE_APPLE_CLIENT_ID` | Apple Services ID для веб-входа. Тот же ID должен входить в серверный `LIFEHUB_APPLE_CLIENT_IDS`. |
| `VITE_APPLE_REDIRECT_URI` | Зарегистрированный в Apple адрес возврата на вашем HTTPS-домене. Apple не допускает здесь localhost или IP-адрес. |

Google использует официальный Google Identity Services, Apple — официальный Sign in with Apple JS. Сервер проверяет выданный провайдером ID token; для Apple используется исходный nonce, SHA-256 которого передан Apple. Без публичных настроек соответствующие кнопки недоступны.

Инструкции провайдеров: [создание Google Client ID](https://developers.google.com/identity/gsi/web/guides/get-google-api-clientid), [веб-вход Apple](https://developer.apple.com/documentation/signinwithapple/configuring-your-webpage-for-sign-in-with-apple). Для локального Google-входа добавьте используемый origin, например `http://127.0.0.1:5173`, в Authorized JavaScript origins клиента.

В Docker значения `VITE_GOOGLE_CLIENT_ID`, `VITE_APPLE_CLIENT_ID`, `VITE_APPLE_REDIRECT_URI` берутся из **корневого `.env`** и передаются в сборку frontend через build args. После их изменения выполните из корня:

```powershell
docker compose up -d --build frontend
```

При разработке достаточно перезапустить `pnpm dev`. Эти значения включаются в браузерный JavaScript при сборке. `LIFEHUB_RESEND_API_KEY`, `LIFEHUB_OPENAI_API_KEY`, JWT/OTP secrets, ключ шифрования и Google Calendar client secret остаются только на сервере; их нельзя добавлять в переменные `VITE_`.

## Google Calendar

Для подключения календаря включите Google Calendar API и настройте серверные переменные:

```dotenv
LIFEHUB_GOOGLE_CALENDAR_CLIENT_ID=ваш_web_client_id
LIFEHUB_GOOGLE_CALENDAR_CLIENT_SECRET=ваш_client_secret
LIFEHUB_CALENDAR_REDIRECT_URIS=["http://127.0.0.1:5173/calendar/callback"]
```

Значения выше — шаблон. Последний адрес подходит при открытии приложения через `http://127.0.0.1:5173`. Интерфейс вычисляет возврат как `${window.location.origin}/calendar/callback`; если вы используете localhost или другой домен/порт, настройте именно этот адрес. В Google OAuth-клиенте добавьте **тот же точный адрес** в Authorized redirect URIs. Для режима Google Testing добавьте свой аккаунт в тестовых пользователей.

После изменения серверного `.env` пересоздайте API и worker:

```powershell
docker compose up -d --force-recreate api worker
```

Откройте настройки календарей и нажмите подключение Google. Вход происходит через Google; `state` сохраняется во вкладке и проверяется после возврата. Страница `/calendar/callback` передаёт `code` и `state` в авторизованный `POST /api/v1/planning/calendar-connections/google/callback`. Этот backend POST не следует указывать как адрес браузерного возврата.

Подключение и синхронизация требуют Pro либо активного Trial. Worker сначала отправляет изменения наружу, затем начинает обратную фазу не раньше чем через секунду. Интервал очередного цикла по умолчанию — 300 секунд. В настройках доступны ручная синхронизация, её состояние и отключение.

## Apple Calendar, письма и ИИ

Apple Calendar требует приложения на iPhone с разрешением EventKit. В браузере новое подключение недоступно; кнопка объясняет это ограничение. Серверный обмен описан в [calendar-sync.md](calendar-sync.md). Нативное приложение iPhone не входит в текущий веб-проект. Apple-вход и Apple Calendar — разные подключения.

Регистрация и восстановление доступа требуют настроенного Resend на сервере. Почтовые напоминания также отправляются через Resend; push требует отдельного шлюза доставки. ИИ-ввод требует серверного OpenAI API key и использует лимиты и права текущего аккаунта. При отсутствии ключей или отказе провайдера интерфейс показывает ошибку; успешная отправка или подключение не подменяются демонстрацией.

## Проверки

Из папки `frontend`:

```powershell
pnpm test
pnpm build
```

Проверяются обновление сессии и ошибки API, изоляция демо, календарные даты и DST, пересечения в календаре, сохранение start-only задач, секунд и осенних смещений времени при редактировании. Сборка включает проверку TypeScript. Отдельные backend-тесты подтверждают planning-only onboarding, совместимость старого выбора и явный Trial. Актуальные результаты запусков — [verification.md](verification.md).
